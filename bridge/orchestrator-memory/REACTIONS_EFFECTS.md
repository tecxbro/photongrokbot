# Reactions, effects and first use

Follow the [operating contract](../../docs/product-repair/OPERATING_CONTRACT.md): acquire a current processing claim and read/resolve the bound context before choosing reaction, effect or no reaction. A natural tapback may acknowledge a message; it never substitutes for requested work. Prefer plain text for ordinary substance and at most one deliberate effect per turn.

Use a canonical structured submission. Reaction payload is `{kind:"react",spaceId,targetMessageId,emoji}`; ordinary reaction purpose is progress, with the original current claim and a stable action key. Text supports a validated effect such as confetti, slam, loud, gentle, invisible, fireworks, balloons, heart, lasers, celebration, sparkles, spotlight or echo. Effect composition restrictions are enforced by the wrapper; do not bypass them with raw SDK calls.

On first authorized supported input, atomic acceptance reserves one onboarding identity and greeting with confetti. First bare hi produces no competing answer; first substantive/non-text input also reaches Front Door work. Agents do not independently enqueue setup confetti or write a celebration marker. Queue/unknown/accepted states remain different. Migrated celebration prevents repetition without claiming device observation.

Any added emoji on a known option returns that exact option's existing details, known price and direct URL immediately. Do not use positive/negative sentiment to choose another workflow or ask whether details are wanted. Missing price is never invented. One ambiguous target gets one concise clarification. Removal is not a new selection; the locked SDK's received stream currently emits added reactions only, so do not invent removal support.

A reaction is never purchase, booking, payment or cancellation authorization. Image Cards does not own the conversation merely because it rendered a card. Metadata and exact provider parts remain in canonical storage; no reaction history is written into a global personal roster.
