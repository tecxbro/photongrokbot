## Interfaces used by runtime and Live Mini

- `submitOutbound(raw, { store, paths?, signal?, normalize? })` validates strict protocol v1, derives the destination and line from the current fenced batch/task, validates every original staged path before conversion, and atomically enqueues. It returns canonical `OutboundStatus[]` (ID, state, attempt count and available provider reference/code). The optional normalizer injection is for tests.
- `createOutboundDispatcher({ store, resolveSpace, paths?, concurrency?, timeoutMs?, maxAttempts?, random?, onError? })` returns `notify()`, `drain()` and bounded `stop()`. The injected resolver receives `{spaceId,lineId}`; its returned `.id` and `.phone` must match both. Runtime owns the single Spectrum client, singleton process lock, startup `recoverSending()` and periodic notifications. No SDK connection is created here.
- `drainCardsReady({ store, paths?, signal?, maxPerTick? })` examines at most four pending rows by default, with a key cursor and fair wrap. It uses the same canonical submission key as Front Door, and removes a pending marker only after successful idempotent enqueue. The default is a product policy; the supported bound is 1–16 rows per tick.
- `resolveReactionOption(store, destination, target)` is synchronous. `applyResolvedOptionToInbound` preserves the exact mapping; `formatOptionSelection` emits existing details, known price/qualifier and original URL for any added emoji. `optionSelectionActionKey` uses the event identity for resolved selection and one stable key for ambiguity on that batch/target. Removed reactions do not select an option.
- Live Mini registers immutable `task-card-context/cardId` plus `task-card-url/fullURL` through the store's fenced `registerPresentation`, then submits `presentation:{cardId,taskId,viewUrl,claimId}`. The atomic enqueue ledger is `presentation-submission` with `{cardId,taskId,viewUrl,claimId,batchId,actionKey,destination,outboundId}`. Configured task-view URLs, registered URLs and edits to registered original cards cannot bypass this context. Unrelated static app URLs retain normal support. A private Live Mini env file supplies the configured origin if setup crashed before the metadata write; malformed existing config fails closed.

## Executable producer commands

Run from the installed bridge with its intended private instance environment and pinned Bun. JSON is read with the existing bounded stdin reader; do not interpolate message bodies into shell commands.

```sh
bun src/enqueue.ts --json-stdin < authorized-submission.json
bun src/enqueue.ts --cards-ready --json-stdin < authorized-card-marker.json
bun src/enqueue.ts --stage-file /absolute/operator-selected/image.jpg
```

A card marker is exactly `{submission,expectedCount,revision,readyAt}`. `submission` is a normal fenced protocol-v1 request with `purpose:"final"`, `payload.kind:"attachment_group"`, matching payload/submission `batchId`, and `actionKey:"cards:<batchId>:<revision>"`. Ordered `attachmentPaths` and `cards` arrays must both contain exactly `expectedCount` entries, at least four. Every entry remains in one group. `readyAt` is an ISO date string. Missing files keep the marker pending; they are never removed from the array. Semantically identical marker retries can refresh the currently authorized claim and producer time; the logical payload and revision cannot change. Expired/stale claims never gain authority by refreshing JSON.

The staging command is an explicit local operator action, not a send grant. It accepts a bounded regular source file, rejects private-instance/secret-like paths and symlinks, and writes a private staged artifact. A live claim and exact destination are still required to send. Legacy modality flags remain adapters to the same protocol and require explicit space, batch, run, generation, action key and purpose. Unknown/duplicate/incompatible flags and model-supplied role/authorization/line overrides are rejected. CLI summaries omit message bodies, URLs, tokens and claim material.

## Deployment, recovery and rollback handoff

Do not replay unknown operations. Before activating the integrated release, use the coordinator's private-state migration/backup procedure and ensure the previous runtime process is stopped. Start only the integrated runtime with its canonical instance root and singleton owner; no helper starts a second Spectrum connection. Runtime startup recovers saved sending attempts to unknown. Inspect exact operation IDs/status and the `provider-late-reference` or `provider-unsettled-reference` record for an exact attempt if present; reconcile only through the explicit operator recovery CLI with verified exact provider evidence. Absence of a reference is not evidence of non-delivery.

If rollback is required, stop the new runtime first, retain the migrated database and uncertain-attempt journal, and restore code/config according to the coordinator backup runbook. Do not restore an older queue snapshot and resend operations whose provider calls might have run. There is no automatic downgrade from SQLite to legacy mutable JSON queues.

Remaining external gates: real Spectrum destination/line resolution and unsupported-capability behavior in the deployed account, message/reference availability, all-modality physical-device receipt/rendering, group parent/part behavior on the target device, native Live Mini original-card refresh, and real lifecycle typing must be observed after separate deployment authorization. Uncancellable SDK calls can remain in flight after a logical deadline; unresolved work is capped and cannot be retried automatically. If the database is entirely unavailable after provider acceptance, the exact reference cannot be guaranteed durable; the preexisting sending attempt preserves the uncertainty boundary. Shared-VM administrators remain trusted; this does not claim OS-level isolation among processes running as the same user.
