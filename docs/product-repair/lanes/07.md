# Lane 07 — canonical task-card recovery

The Node 22 helper publishes host content and submits one initial app operation through the existing bridge. It does not import SQLite, instantiate Spectrum, use a raw JSON queue, or accept an optional direct-send runtime. The standalone injected presenter retains its original claim/settle behavior and now rejects changes to the full card URL. The VM integration example uses the canonical helper.

## Actual interfaces

Run controls from the bridge checkout with pinned Bun 1.4.2:

- `bun run src/presentation-control.ts task-context --json-stdin` takes `{taskId,batchId,claim?}`. It reads the accepted/completed native task and original batch destination and returns `{taskId,batchId,destination:{spaceId,lineId},origin}`. Supplying `claim` additionally validates its current generation and lease.
- `bun run src/presentation-control.ts register --json-stdin` takes `{claim,context:{cardId,taskId,batchId,destination,viewUrl}}`. Registration is immutable and transactional; it validates the configured HTTPS origin, exact `/live-1` through `/live-10` route/card ID, private `k` query token, task, batch, destination, and current claim.
- `bun run src/presentation-control.ts operation-status --json-stdin` takes `{taskId,batchId,actionKey}` and returns `{items:OutboundStatus[]}` for the original destination and fixed purpose `presentation`. This read supports reconciliation after claim expiry.
- `bun run enqueue -- --json-stdin` remains the only helper submission path. The helper sends protocol v1, original batch/task/current claim, stable action key, `purpose:"presentation"`, `payload:{kind:"app",spaceId,url,live:true}`, and `presentation:{cardId,taskId,viewUrl,claimId}`. The database atomically retains the presentation-submission metadata, immutable one-card operation reservation, and outbox row.

The new package alias requested from the coordinator is `presentation-control: bun run src/presentation-control.ts`. Node invokes exact source entrypoints without a shell. Request/output budgets are 65,536 bytes and the control deadline is ten seconds. Rejected controls return only generic errors; full URLs and provider references cross private child pipes, never routine logs.

```js
import { createLiveCardMilestones } from './live-card-milestones.mjs';
const cards = createLiveCardMilestones({
  taskContext: { taskId, batchId, claim: { batchId, runId, generation } },
});
const first = await cards.createCard(createPayload, stableTaskKey);
await cards.sendOnce(originalSpaceId, first.record.viewUrl, stableTaskKey);
await cards.updateMilestone(first.record.id, {
  requestId: stableMilestoneId,
  expectedRevision: revisionUsedToComputeThisContent,
  content: authoredSnapshot,

await cards.completeAndRelease(first.record.id, stableTaskKey);
```

The native task must already have its durable intent followed by actual acceptance receipt recorded through batch control. Its original destination is derived, never chosen by the helper. `createPayload.taskId` and `conversationRef` must match that binding; `requestId` and `stableTaskKey` are explicit caller-owned identities. `loadContext(taskKey)` is asynchronous. `completeAndRelease(cardId,taskKey,terminalUpdate?)` accepts an optional full `{requestId,expectedRevision,content}` update body before release. Ordinary updates and terminal content require a current claim. A process with an expired claim can still read exact outbox status and settle a previously accepted initial send; it cannot author new host content.

## Durable boundaries and recovery

The helper resolves the canonical instance root, validates private `instance.json`, and reads publisher configuration only from `secrets/live-mini.env` unless explicitly injected by its trusted caller. A custom `paths.root` still goes through the shared resolver and its environment/test guard. Checkout state/secrets overrides are rejected. A legacy `runtime/state` directory stops the helper with `LEGACY_CONTEXT_REVIEW_REQUIRED`; preserve/archive it through the migration review rather than treating it as fresh empty state. Migrated legacy records remain quarantined evidence and do not grant new send authority.

Each private context filename is SHA-256 of installation ID, full task ID, batch ID, original space/line, and complete task key. A separate per-context kernel flock serializes Node writers. A minimal Python holder receives no publisher environment and holds the lock only while the Node owner's input pipe remains open. Owner SIGKILL closes that pipe; holder death fences the helper. There are no stale timeouts or lock-file stealing. Existing lock files are reusable kernel lock identities, not abandoned work indicators.

| Interrupted boundary | Durable identity | Recovery |
| --- | --- | --- |
| Create | Original create body/request ID and action key saved before HTTP | Replay identical create or read the already known card; changed body conflicts |
| Host presentation claim | Saved begin intent/revision before HTTP | Read the same card's active send attempt; adopt its exact returned claim ID after a lost acknowledgement |
| Enqueue | Saved card URL/claim plus immutable registered context | Query exact operation status first; a committed operation is recovered by its stable action key, never replaced |
| Provider request | Durable bridge dispatch attempt | A crash becomes unknown in the bridge; no automatic physical resend |
| Host settlement | Exact outbox provider message ID and saved settlement intent | Repeat the identical settlement only; no enqueue when the operation already exists |
| Milestone write | Separate exact update-body journal before HTTP | Retry only the same request/body/revision after unknown response; no automatic rebase |
| Terminal release | Original URL, terminal content, reconciled outbox message ID | Retry/read release for the same card; normal progress never edits or resends the app |

Definitive `REVISION_CONFLICT` and `IDEMPOTENCY_CONFLICT` responses remain visible and mark the exact update journal as rejected. The caller may review current content and intentionally author a new request with its explicit revision. The helper never changes the request ID or expected revision itself. A pending unknown update continues to reject a different body. A changed path or access token rejects before replacing the previous context, with no URL in the error. Token rotation requires a separate explicit migration.

Unknown, timed-out, failed, cancelled, or accepted-without-message-ID initial sends retain the host claim/slot for evidence reconciliation. Do not create a replacement card/action. After exact operator reconciliation of the existing outbox record, call the same `sendOnce` with the same task key and full URL: it reads status and settles that original host claim. Release requires terminal content, no active host attempt, and equality between host message reference, local settled reference, and accepted outbox provider evidence.

Expired accepted native tasks use the existing offline, kernel-locked `recover-delegation` path with an exact original task ID and recorded receipt/status. Recovery preserves task/batch/destination, fences the previous generation, and wakes reconciliation; it does not invoke or repeat a native task. An unexpired accepted worker is rejected. Renew a current invocation during long work; do not invent new task IDs to bypass an expired claim.

## Final review follow-up

Private helper configuration is read through a private regular-file descriptor with a 64 KiB stat/read budget. Only `PUBLIC_BASE_URL` and `PUBLISHER_TOKEN` are accepted; both are required in an existing file. Duplicate/unknown keys, empty values, control characters, unmatched quotes, oversized files, invalid UTF-8 and non-bare HTTPS origins fail with generic `CONFIG_ERROR`. Quoted values are literal; shell/environment expansion never occurs. Trusted test injections do not bypass validation of an existing malformed file.

A persisted `create_intent` without a card ID must still validate its current claim before replaying create HTTP, because that request might allocate its first card. A stale updater validates before writing its update journal, so a rejected unsent request cannot block a newly fenced successor. Tests prove zero host writes and unchanged context/journal on both stale paths, followed by a valid successor's explicitly authored update.

The publisher HTTP client accepts only stable codes emitted by the bundled host source and replaces every remote error message with fixed generic text. Unknown codes and malformed error bodies become `HOST_ERROR`/`HOST_RESPONSE`; a host response cannot echo a private token or full view URL into helper/CLI exceptions. Known revision/idempotency conflict codes remain available for recovery decisions. Seeded-secret tests verify both message and code redaction.
