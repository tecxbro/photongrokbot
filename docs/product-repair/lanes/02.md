# Lane 02 — storage, claims, migration and local recovery

## Implemented boundary

Schema v1 (`PRAGMA user_version=1`) is a single private SQLite database. `instance` binds the file to the installation ID already committed by explicit setup; normal `openStore()` is `create:false`. Tests inject their own paths and identity. Importing a module never creates state. Corrupt, missing, mismatched, symlinked, non-private or unsupported storage fails closed. No read failure recreates an empty queue. `inspectDatabase`/`openStore({readOnly:true})` never repair permissions or change journal mode.

The store is synchronous and every logical transition uses a short immediate transaction. Provider calls, subprocess work, attachment preparation and webhook requests happen outside transactions. Foreign keys are on, synchronous durability is FULL, and busy waiting is bounded to 2 seconds. WAL requires a verified local filesystem type and an actual patched SQLite version/source ID. Bun 1.4.2 on the development Mac reports SQLite `3.54.0`, source `2026-04-09 12:25:13 8fa8248e303219400c646a885e36dfc52eae33d83f4412e3f369b2be5373aapl`. This is local evidence, not a claim about the VM. The WAL-reset fix floor is 3.51.3, including upstream backports 3.50.7 and 3.44.6. WAL is initialized before the first schema write so fresh read-only tools have valid WAL/SHM state.

| Tables | Purpose |
| --- | --- |
| instance, metadata | Installation identity; setup/onboarding/mapping/checkpoint state |
| inbox, targets | Unique event identity, durable pending eligibility, original conversation and known message IDs |
| batches, batch_events | Immutable ordered per-conversation membership, fenced processing generation |
| wakes | Durable bounded wake attempts, separate from task completion |
| tasks | Stable native delegation intent and receipt; unknown acceptance holds ownership |
| operations, outbound, attempts | Unique logical action, all intended child bubbles, durable provider attempt/evidence |
| media_jobs | Serialized restart reference, attempt-fenced enrichment of the original input |
| migration | Committed immutable source digest and recovery report |

Acceptance commits the input, pending state and installation-scoped Grokbot greeting/confetti action together. Only the first bare greeting is answered exclusively by that action; later greetings and substantive first input remain eligible for routing. Batch formation commits membership and a wake together. Claim/renew/complete/enqueue checks compare exact run ID, generation and live lease. A bot name never resumes a different invocation. Native intent is committed before handoff; unknown intent cannot be replaced with a second task.

Enqueue validates and prepares all children before one transaction. Conversation/line/purpose/action plus canonical payload determine operation identity: same payload returns original IDs; changed payload rejects. Claiming the next operation records an attempt before provider dispatch. Unresolved content blocks later content in that conversation; typing controls and unrelated conversations can continue. A recovered `sending` operation becomes `unknown`, never `queued`. Settlement writes reference, attempt evidence, poll/session/ordered presentation mapping and onboarding state atomically. External live-host settlement is a separate recoverable metadata job. Presentation submissions pass `context.presentation` to enqueue; every child row receives immutable `presentation-submission` metadata in that same transaction. Its shape is `{cardId,taskId,viewUrl,claimId,batchId,actionKey,destination,outboundId}`; batch/action/destination come from the validated enqueue context. Replays compare the complete ledger, including missing versus present metadata, and reject changed presentation identity rather than overwriting it. The metadata is allowed only for app/app_update payloads with the exact same view URL, and supplied task IDs must agree.

Wake acknowledgement does not complete a batch. A pending batch not claimed within 60 seconds after acknowledgement becomes eligible for a repeat notification; claimed/delegated work is not re-notified. Runtime must call `recoverSending()` and `recoverWork()` once after acquiring its exclusive lifetime instance lock, never per store open. Media recovery increments attempts; stale results cannot replace the new worker's result. No media result creates a second batch/task.

## APIs for other lanes

The frozen `BridgeStore` contract remains primary. `storage.contract.ts` documents additional local methods: `batchDestination`, `claimSnapshot`, `tasksForBatch`, `recentInbound` (at most 100), `listOutbound` (at most 10,000; diagnostic only), `listMetadata` (at most 1,000), indexed `operationStatus`, `deleteMetadata`, `activeConversationWork`, `recoverWork`, `backupTo`, `sqliteFacts`, and retention/reconciliation APIs. `readBatch` includes current media jobs and task bindings. Presentation metadata uses `presentation` keyed by batch ID and `presentation-index` keyed by parent provider ID; poll keys use `poll`, app sessions use `app-session` and preserve all four session fields. Legacy originals are in the immutable backup and `legacy-source` metadata when relevant.

Typing activity comes only from unexpired claimed/delegated batches without a terminal/unknown final action. Accepted progress does not stop typing. Lease expiry removes abandoned activity.

Retention removes resolved body content while preserving event dedupe, operation hashes, original provider references and unresolved/active work. Exact unused intermediate candidates can be provided by lane01's scoped scanner; the store protects retained references and does not select them while media jobs are active. Cleanup paths are durable `retention-cleanup` intents, returned after restart until `acknowledgePrunedArtifacts(paths)` records successful removal or absence. The migration backup intentionally preserves original private data for recovery; operators must apply their backup-retention policy separately. `backupTo` serializes a consistent SQLite snapshot to an exclusive 0600 private backup and fsyncs it. Do not copy only a live main `.sqlite` file.

## Offline migration and rollback

1. Stop all legacy writers and pending agent enqueue work. Preserve identity, authorization and secret files. Initialize the new private installation through the explicit lane01 setup path; migration requires that identity and does not rewrite `instance.json`.
2. Work from a private copy first. Run `bun run src/migrate-legacy-state.ts --source /absolute/legacy-data-copy --line-id ACTUAL_LINE_ID`. Dry-run reads inputs and emits a redacted issue inventory; it writes neither source nor target. Legacy records with a stored line ID keep it. The explicit fallback must be the actual original line, not a guessed destination.
3. Inspect malformed/dangling/conflicting records. The parser rejects malformed JSON and read denial; it never substitutes empty state. Mixed conversations, contradictory membership, dangling wakes and ambiguous handoffs are retained/reported for review. No provider operation is authorized by migration.
4. With old writers confirmed stopped, use the same exclusive lock wrapper as runtime: `bun run src/run-locked.ts -- bun run src/migrate-legacy-state.ts --source /absolute/legacy-data --line-id ACTUAL_LINE_ID --apply --writers-stopped`. The CLI checks the held instance lock and refuses a live legacy `runtime.pid`. Since old writers did not honor the new lock, the stopped-writers attestation and process inventory remain an operator gate.
5. Apply records an immutable attempt digest, copies the entire regular-file source to `backups/legacy-DIGEST`, verifies source/backup digests, marks the backup read-only, and commits one import/version marker transaction. File contents changed after an attempt require reconciliation, never an additional import. A same-source rerun returns the original report. The source cutover marker is repairable after a crash between DB commit and marker write.
6. Legacy `sent` becomes `accepted` with `LEGACY_ACCEPTED_EVIDENCE`; missing provider IDs stay missing. Every legacy `queued` becomes `unknown`/`LEGACY_DISPATCH_UNCERTAIN`, even with attempts zero. Existing greeting/confetti markers reserve onboarding with `legacy-marker-not-device-observation` provenance and do not resend. Handled IDs are consulted during fresh acceptance even when the new event-key format differs. Poll, full mini-app session, ordered option/presentation and task/helper records are preserved. Legacy delegation records become review-needed unknown native ownership until exact receipt reconciliation.
7. Start only the repaired runtime after reviewing recovery inventory. Roll code back only to a schema-compatible repaired version using the same DB. Never launch the historical JSON queue writer or restore an older DB snapshot and resume sending: database rollback cannot undo provider effects and can replay already accepted messages. Keep the cutover marker and the original backup. A full restore is an offline forensic/reconciliation operation; unresolved provider history must be reconciled before dispatch resumes.

## Operator-only reconciliation

These commands require the exclusive runtime lock (therefore runtime stopped); they record evidence without calling Spectrum or native tools. They provide no retry/replay operation.

- `bun run src/run-locked.ts -- bun run src/outbound-status.ts --resolve-json-stdin` accepts `{id,state:"accepted",evidence,reference:{messageId,...}}` only with an exact provider reference and explicit evidence, or `{id,state:"cancelled",evidence}` to record external non-application/abandonment. It only transitions an `unknown` item; keeps attempt count, action identity and audit history; and atomically updates derived mappings.
- `bun run src/run-locked.ts -- bun run src/batch-control.ts recover-delegation --json-stdin` accepts `{taskId,state:"accepted"|"completed",receipt}`. It preserves the original unknown task ID, records the native receipt, fences the old claim, and makes that original batch eligible for a fresh claim. `read-batch` exposes the binding so an agent continues it without issuing another native handoff.
- Normal `batch claim`, `renew`, `complete`, `delegation-intent`, `delegation-receipt`, `read-batch` and `outbound-status --id` remain separate bounded controls. Completion of a processing claim is not a claim of device delivery.
